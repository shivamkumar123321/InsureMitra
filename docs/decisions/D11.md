## Status and decision

**Resolved for the current BUILD plan; T04 verification passed on 2026-10-26.** Use the authenticated `gpt-6-luna` model through the OpenAI Responses API for the initial text-reasoning integration. The user requested a small, low-cost model and confirmed a project-specific `$5` spend limit, that this is the only project they use, and an expiry date of 1 Jan 2028. These are user-reported account facts, not independently visible in the API. No billing controls were changed. Current balance, billing mode, auto-recharge status, and exact meaning/scope of the reported expiry remain unverified and must not be represented as verified facts.

The bounded fictional-text request succeeded (HTTP 200, completed, 15 input and 6 output tokens). At the published standard text rates, the token-based estimate is `$0.0000045` before account adjustments. This confirms the selected model is enabled and can produce a response; it does not verify the account balance or future availability.

OpenAI documents that prepaid exhaustion and hard-spend-limit enforcement may lag, and recorded spend can slightly exceed a configured limit. Therefore the user-reported `$5` project limit is the provider-side spend control for this project, not a guaranteed instantaneous no-overage boundary. The user has confirmed they accept using this dedicated project within that limit. Do not raise, remove, or otherwise change the limit. Do not add application session/request caps. No guarantee of zero overage, free use, or future availability is made.

## Failure and state-preservation policy

- Keep the OpenAI key server-side in environment configuration; never expose it to the browser or logs (SPEC P3).
- Save the last confirmed profile and completed recommendation results before starting a reasoning request. Treat generated text as advisory; it cannot overwrite confirmed profile data or eligibility/ranking results.
- If a request times out, is interrupted, or returns an error, retain that saved state and show that new AI answers are unavailable or pending. Do not claim the two-second response target was met.
- Do not automatically retry an ambiguous timeout or connection loss: the provider may have accepted and billed the first request. Offer an explicit user retry while preserving state. A future implementation may retry only when the response proves the first request was rejected before processing, and must honor provider retry guidance; it must not silently replay an ambiguous paid generation.
- Exact application timeout durations, retry implementation details, and state-transition tests are deferred to their implementation tasks because the application does not exist yet. No unsupported timeout or retry count is invented here.
- When reasoning is unavailable or credits are exhausted, preserve the profile/results and clearly state that new AI answers are unavailable, as required by SPEC §15.
